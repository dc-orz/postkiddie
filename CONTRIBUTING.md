# 参与贡献

[English below](#contributing-in-english)

欢迎 issue 和 PR。这份文档只讲「怎么参与」，代码风格与目录职责等细节在
[docs/conventions.md](docs/conventions.md)，技术决策的来龙去脉在
[docs/architecture.md](docs/architecture.md)。

## 环境准备

需要 Node ≥ 22.12、pnpm、Rust stable（≥ 1.88）、git，以及各平台的
[Tauri 前置条件](https://v2.tauri.app/start/prerequisites/)。

```bash
pnpm install     # 顺带通过 prepare 脚本装好 git hooks
pnpm app:dev
```

## 提交之前

`pnpm install` 会装上 lefthook，所以大部分检查是自动的：

| 时机 | 跑什么 | 大约耗时 |
|---|---|---|
| `pre-commit` | 格式化 + 可自动修的 lint（仅暂存文件） | < 1s |
| `commit-msg` | Conventional Commits 校验 | 瞬间 |
| `pre-push` | 类型检查、clippy、全部测试 | 数十秒 |

想手动跑一遍全量检查：

```bash
pnpm check          # lint + 类型 + 对比度 + rustfmt + clippy
pnpm test           # 前端测试
pnpm rs:test        # Rust 测试
```

**改了 Rust 侧的模型或命令签名，必须跑一次 `pnpm rs:test` 并提交重新生成的
`src/types/bindings.ts`。** 那个文件由 specta 生成、请勿手改；CI 有一步
`git diff --exit-code` 专门拦「改了模型却没提交绑定」——那类漂移不会让编译失败，
只会在运行时让前端拿到对不上的数据。

## 提交信息

[Conventional Commits](https://www.conventionalcommits.org/)，由
`scripts/check-commit-msg.sh` 校验：

```
<type>(<scope>): <描述>
```

类型：`feat` `fix` `docs` `style` `refactor` `perf` `test` `build` `ci` `chore` `revert`
范围（可选）：`git` `http` `storage` `ui` `tokens` `domain` `terminal` `workspace` …
标题上限 72 字符——超过会在 `git log --oneline` 和 GitHub 列表里被截断。

正文值得写。这个项目的注释和提交信息都倾向于**记录理由而非结论**：
将来推翻某个决定时，先要知道它当初成立的前提是什么。

## 写测试的判断标准

**这段逻辑出错时，会不会静默地产生错误结果？** 会的话就写。

git status 解析错了不会报错，只会让 UI 显示错的文件状态；diff 行号算错了不会抛异常，
只是让你看到一份「看着对、其实错位」的差异。这类地方必须有测试。

- Rust：与实现同文件的 `#[cfg(test)] mod tests`；跨进程/真实 git 的行为放
  `src-tauri/tests/`
- 前端：`*.test.ts(x)`，与被测文件同目录，Vitest + jsdom

写完新测试后，值得**把修复临时去掉再跑一遍**，确认它真的会失败——否则可能写了一个
永远通过的测试。

## PR 说明里请写清

- 解决什么问题（而不只是改了什么）
- 如果引入了新依赖：为什么标准库或已有依赖做不到。这条不是形式主义，
  已经被否掉过几个（commitlint 全家桶、Pillow、ESLint + Prettier）
- 如果改了 design token：`pnpm check:contrast` 的结果
- 如果改动能在界面上看见：截图或录屏

## 报 issue

用 issue 模板。最有用的信息是**复现步骤**和**平台/版本**——这个项目在三个平台上
各有各的坑（路径分隔符、git CLI 输出差异、WebView 内核差异），缺了平台信息往往无从下手。

# Contributing (in English)

Issues and pull requests are welcome.

Note that the design documents under `docs/`, the code comments, and most commit messages
are written in **Chinese**. You are welcome to write issues and PRs in English — but be
aware that reading the reasoning behind existing decisions will require translation.

## Setup

Node ≥ 22.12, pnpm, Rust stable (≥ 1.88), git, plus your platform's
[Tauri prerequisites](https://v2.tauri.app/start/prerequisites/).

```bash
pnpm install     # also installs the git hooks via the prepare script
pnpm app:dev
```

## Before you commit

lefthook runs most checks for you: formatting and auto-fixable lints on `pre-commit`,
commit-message validation on `commit-msg`, and type-checking + clippy + the full test suite
on `pre-push`. To run everything by hand:

```bash
pnpm check      # lint + types + contrast + rustfmt + clippy
pnpm test       # frontend tests
pnpm rs:test    # Rust tests
```

**If you change a Rust model or command signature, run `pnpm rs:test` and commit the
regenerated `src/types/bindings.ts`.** That file is generated by specta — never edit it by
hand. CI fails on drift, because drift does not break the build; it silently hands the
frontend data that no longer matches its types.

## Commit messages

[Conventional Commits](https://www.conventionalcommits.org/), enforced by
`scripts/check-commit-msg.sh`. Subject line max 72 characters.

Write the body. This codebase consistently documents *why*, not *what* — the reasoning is
what you need when you later want to overturn a decision.

## When to write a test

**Would a bug here fail silently?** If yes, write the test.

A mis-parsed `git status` throws nothing — it just shows the wrong file state. A diff with
off-by-one line numbers renders fine and is wrong. Those need coverage. After writing a test,
temporarily remove the fix and confirm the test fails; otherwise you may have written a test
that can never catch anything.

## In your PR description

- What problem this solves, not just what changed
- For a new dependency: why the standard library or an existing dependency can't do it
  (several have been rejected on these grounds)
- For design token changes: the `pnpm check:contrast` output
- For visible changes: a screenshot or recording
